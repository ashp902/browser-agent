# 03 - Element Registry and Action Executor

Status: AUTHORITATIVE FOR MVP

## 1. Objective

Provide a deterministic bridge from model-visible opaque element IDs to live DOM elements, then execute only a small fixed set of validated actions.

## 2. Element registry

A registry is created once per document content-runtime instance.

Required internal structures:

```ts
class ElementRegistry {
  private nextId = 1;
  private elementToId = new WeakMap<Element, number>();
  private idToElement = new Map<number, WeakRef<Element> | Element>();
}
```

If `WeakRef` is used, code MUST tolerate collection. If browser compatibility or tests make `WeakRef` awkward, strong reverse references are allowed for MVP and cleared on document unload.

### 2.1 ID assignment

`getOrAssignId(element)`:

- returns existing ID if node already registered;
- otherwise assigns `nextId++`;
- ID never changes for the same live DOM `Element` during the document lifetime;
- ID is never intentionally reused in the same document.

IDs reset when a new content-script document initializes.

### 2.2 Registry is not model memory

The registry is an implementation mapping, not a semantic identifier. The model must re-observe after navigation or stale-target errors.

## 3. Document identity

At content-script startup:

```ts
const documentId = crypto.randomUUID();
```

This ID is returned in every observation/action result.

Any action with a different `document_id` MUST fail `DOCUMENT_CHANGED` without touching DOM.

## 4. Action envelope

```ts
interface BrowserActionRequest {
  protocol_version: 1;
  action_id: string;
  document_id: string;
  observed_mutation_epoch: number;
  tool: BrowserToolName;
  args: unknown;
  expected_target?: SemanticFingerprint;
}
```

`action_id` is a UUID generated by backend/orchestrator and used for idempotency/logging.

## 5. Allowed MVP tools

Exact external tool names:

```text
click_element
set_text
select_option
set_checked
press_key
scroll_page
scroll_element
navigate_current_tab
go_back
```

`observe_page` is an observation request, not an executor mutation tool. `finish` exists only in orchestrator/model tool space.

## 6. Common target validation

Before executing any element-targeted action:

1. Verify `document_id`.
2. Resolve `element_id`.
3. Verify element still exists and `element.isConnected`.
4. Recompute minimal role/name/type fingerprint.
5. Compare to `expected_target`.
6. Verify target supports requested action.
7. Verify target is not disabled/read-only as appropriate.
8. Verify target is not semantically hidden.
9. Scroll into view if action requires interaction.
10. Re-check connection/state immediately before action.

### 6.1 Mutation epoch behavior

Do NOT reject merely because `current_epoch != observed_mutation_epoch`.

Modern pages mutate constantly. Instead, epoch mismatch triggers stricter target revalidation. If semantic fingerprint still matches and target is connected, action may proceed.

This rule is intentionally frozen.

## 7. Fingerprint matching

A target is stale if strong fields conflict:

- role changed materially;
- normalized accessible name changed from non-empty to a different non-empty name;
- element tag/input type changed impossibly;
- link origin changed when the action depended on the link identity.

Minor descriptive text changes do not automatically stale a control.

If stale, return:

```json
{
  "ok": false,
  "error": {
    "code": "STALE_TARGET",
    "retryable": true,
    "message": "The target changed after it was observed. Observe the page again."
  }
}
```

## 8. `click_element`

Schema:

```ts
interface ClickElementArgs {
  element_id: number;
}
```

Supported targets include native clickable elements and elements with supported interactive roles.

Execution:

1. validate target;
2. `scrollIntoView({block: 'center', inline: 'nearest'})` when needed;
3. focus element when focusable and doing so is not destructive;
4. call native `.click()` on `HTMLElement` where available;
5. return immediate structured result;
6. orchestrator observes afterward.

MVP does not synthesize low-level trusted pointer events. Some sites may reject programmatic DOM clicks; classify this as `ACTION_FAILED`/known limitation rather than adding `chrome.debugger` implicitly.

## 9. `set_text`

Schema:

```ts
interface SetTextArgs {
  element_id: number;
  text: string;
  mode?: 'replace';
}
```

Only `replace` exists in MVP.

Supported:

- `<input>` textual types except password and disallowed sensitive types;
- `<textarea>`.

Not supported in MVP:

- password fields;
- contenteditable;
- rich editors;
- file inputs.

Execution for input/textarea:

1. validate target;
2. reject disabled/read-only;
3. reject sensitive-manual field classifications;
4. focus;
5. use native prototype `value` setter rather than only direct property assignment when possible so framework wrappers observe the update;
6. dispatch bubbling/composed `input` event;
7. dispatch `change` only when project tests show the control semantics require it; default behavior is to dispatch both `input` then `change` in MVP reference implementation;
8. verify resulting DOM value equals requested value when readable;
9. return result with value length, not necessarily full value in telemetry.

No clipboard simulation.

## 10. `select_option`

Schema:

```ts
interface SelectOptionArgs {
  element_id: number;
  option_value?: string;
  option_label?: string;
}
```

Exactly one of value or label must be provided.

MVP supports native `<select>` only.

Algorithm:

1. find matching enabled option;
2. if label used, normalize whitespace and require an unambiguous exact normalized label match;
3. update native `value`/selected state;
4. dispatch `input` and `change`;
5. verify selection;
6. return selected label/value.

Custom ARIA comboboxes are navigated through normal click/key actions, not this native-select tool.

## 11. `set_checked`

Schema:

```ts
interface SetCheckedArgs {
  element_id: number;
  checked: boolean;
}
```

Supports native checkbox/radio with restrictions:

- checkbox can set true/false;
- radio can only set true; setting false returns `UNSUPPORTED_TARGET` because radio groups are selected by choosing another radio.

If current state already equals requested state, return success with `changed=false` and do not click.

Otherwise use `.click()` to preserve page event behavior, then verify state.

## 12. `press_key`

Schema:

```ts
interface PressKeyArgs {
  element_id?: number;
  key: AllowedKey;
}
```

Allowed keys in MVP:

```text
Enter
Escape
Tab
ArrowUp
ArrowDown
ArrowLeft
ArrowRight
Home
End
PageUp
PageDown
Space
```

No arbitrary key string and no modifier combinations in MVP.

Because synthetic keyboard events are not trusted and cannot reproduce all browser default behavior, prefer focusing target and using supported DOM/native behavior. If reliable event execution is not possible for a site, fail clearly rather than adding arbitrary event code.

## 13. `scroll_page`

Schema:

```ts
interface ScrollPageArgs {
  direction: 'up' | 'down' | 'top' | 'bottom';
  amount?: 'small' | 'medium' | 'large';
}
```

Deterministic amounts:

```text
small  = 0.35 * viewport height
medium = 0.75 * viewport height
large  = 1.25 * viewport height
```

For top/bottom use page bounds.

Return before/after scroll position.

## 14. `scroll_element`

Supports scrollable containers identified in semantic model.

Schema mirrors page scroll plus `element_id`.

Validate that element has scrollable overflow and non-zero scroll range.

## 15. `navigate_current_tab`

Schema:

```ts
interface NavigateArgs {
  url: string;
}
```

Rules:

- only `http:` and `https:` URLs;
- resolve relative URL against current document URL before policy check;
- no `javascript:`, `data:`, `file:`, `chrome:`, `blob:` in MVP;
- policy engine can require confirmation for suspicious cross-origin navigation;
- implementation can call `location.assign()` from content context for same-tab navigation;
- after navigation, action result may be interrupted by document unload; extension runtime must treat new document observation as authoritative.

## 16. `go_back`

No args.

Perform same-tab history back when possible. If no history entry is available, return a normal no-op result.

## 17. Idempotency

Content executor keeps a bounded LRU cache of recently seen `action_id` values for current document.

If the same action ID arrives twice:

- do not execute again;
- return cached action result if available.

Minimum cache size: 100 action IDs.

This prevents duplicate clicks from network retries.

## 18. Action result

```ts
interface ActionResult {
  protocol_version: 1;
  action_id: string;
  document_id: string;
  mutation_epoch_before: number;
  mutation_epoch_after: number;
  ok: boolean;
  changed?: boolean;
  summary: string;
  data?: Record<string, unknown>;
  error?: ActionError;
}
```

`summary` is concise and safe to show to model/user, e.g. `Clicked button "Add to cart".`

Never put raw page HTML in result.

## 19. Action timeouts

Local DOM action target: 2 seconds maximum excluding navigation load.

The executor itself does not wait for an arbitrary page "network idle" condition. After a mutating action, orchestrator waits a short stabilization window and observes again.

Default stabilization delay:

```text
250 ms
```

If mutations continue, observation logic can debounce. Do not sleep for multi-second fixed delays by default.

## 20. Consequential action metadata

Before execution, local action request includes policy decision from backend. The content script still does not trust it blindly for secrets/manual-only controls.

For an action classified `REQUIRE_CONFIRMATION`, extension must receive a confirmation token bound to:

- task ID;
- action ID;
- target fingerprint;
- normalized action summary;
- short expiration.

This prevents a generic "yes" from authorizing a different action after page changes.

Detailed rules in document 06.

## 21. Tests required

Unit tests for:

- stable ID assignment;
- ID non-reuse;
- new document invalidation;
- stale fingerprint detection;
- unrelated mutation does not invalidate target;
- duplicate action ID idempotency;
- set_text event behavior in React-like input fixture;
- native select success/failure;
- checkbox/radio logic;
- disabled/hidden rejection;
- forbidden navigation schemes;
- sensitive field refusal.

E2E test must demonstrate two repeated `Buy` buttons and verify the correct card's button is clicked by ID.
